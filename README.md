# CMP 30HX / 40HX / 50HX Unlock

[English version](README_en.md)

Патчи и скрипты для графических процессоров NVIDIA CMP **30HX / 40HX / 50HX**
на базе открытых
[open-gpu-kernel-modules](https://github.com/NVIDIA/open-gpu-kernel-modules)
версии **610.43.03**.

Два патча — разблокировка PLM (`cmp_exploit_clean.patch`) и PCIe Gen2
(`cmp_pcie2.patch`) — и три скрипта: собрать (с выбором патчей), попробовать,
поставить навсегда.

> **Важно:** на системе уже должен быть установлен драйвер NVIDIA **610.43.03**
> в варианте открытых модулей ядра (**MIT**, у NVIDIA это вариант `-open`):
> мы заменяем его ядровые модули патчеными, а userspace — `nvidia-smi`, `libcuda` —
> остаётся от него и обязан совпадать по версии.

## Что делает

CMP-карты несут аппаратно-замурованную политику ограничителей (PLM). Патч
встраивает в путь загрузки GSP (в прошивочный бутер-цикл) «трёхвыстрельную
машину»: три контролируемых выстрела по очереди открывают блокировки регистров
GPU, после чего карта грузится стоковой прошивкой уже с разбуженными
ограничителями. Патч работает на всех трёх картах (PCI ID `10de:2189`,
`10de:1f0b`, `10de:1e09`).

По итогам ритуала:

- PLM-замок FECS открыт (`ffffffff`), окно WPR2 сброшено;
- регистры скоростных оверрайдов (SS0/SS1) записаны по-боевому;
- GSP и весь стек драйвера грузятся штатно, карта видна в `nvidia-smi`,
  подпись прошивки для стокового лоада пересобирается — драйвер nowhere знает,
  что его разбудили.

Ритуал безвреден для железа и повторяется на каждой загрузке модуля.

## Что даёт

Живые замеры на **CMP 50HX** (GEMM 4096x4096):

| Метрика | Было | После unlock |
|---|---|---|
| FP32 kernel | 0.853 TFLOPS | **27.117 TFLOPS** |
| FP16 kernel | 54.6 TFLOPS | 54.6 TFLOPS |
| FP32 cuBLAS | 0.422 TFLOPS | **12.495 TFLOPS** |
| FP16 cuBLAS | 3.118 TFLOPS | **88.376 TFLOPS** |
| FP64 | ~0.85 / 0.42 TFLOPS | без изменений (стоко) |

На CMP 40HX и 50HX эксплойт даёт кратный прирост производительности. На CMP 30HX
он открывает простор для экспериментов. PCIe Gen2 (см. ниже) работает на всех
трёх картах.

Несколько CMP-карт в одной машине могут работать вперемешку: ритуал ставится
каждой карте отдельно и другим картам не мешает.

## Как это работает

Патч добавляет в GSP-путь модуля машину из трёх «выстрелов». Каждый выстрел —
это подделанная подпись прошивки, с которой бутер по своей уязвимости выполняет
короткую цепочку записей в PRI-регистры GPU:

| Выстрел | Что открывает |
|---|---|
| 0 | `FECS_PLM` → `ffffffff` (снимает замок FECS) + служебная цепочка |
| 1 | `WPR2` (Write-Protected Region 2) гасится, PLM-цепочка |
| 2 | финальная цепочка; между выстрелами пишутся оверрайды скорости `SS0/SS1` |

После каждого выстрела оригинальная стоковая подпись восстанавливается, а после
третьего драйвер делает обычный стоковый `BooterLoad` — и GSP взлетает на уже
разбуженной карте. Квота — ровно три выстрела за жизнь модуля, дальше драйвер
абсолютно стковый.

## Патчи и выбор

| id | Файл | Что делает |
|---|---|---|
| `exploit` | `cmp_exploit_clean.patch` | разблокировка PLM/GSP (см. «Что делает») |
| `pcie2` | `cmp_pcie2.patch` | PCIe Gen2 x16 (см. «PCIe Gen2») |

Патчи независимы — можно накладывать по отдельности или оба. Сборка спрашивает,
что накладывать:

```bash
./cmp-build.sh                      # интерактивный выбор (номера/id/all)
./cmp-build.sh --patches=all        # неинтерактивно: оба
./cmp-build.sh --patches=exploit    # только разблокировка
./cmp-build.sh --dry-run --patches=all   # только проверить применимость
```

Уже наложенный патч определяется по маркеру в исходниках и пропускается —
повторный запуск безопасен. Третий патч = одна строка в каталоге `PATCHES`
наверху `cmp-build.sh` + файл патча рядом со скриптом.

## PCIe Gen2

Карта стоково сидит на Gen1 (2.5 GT/s). Патч `pcie2` в двух местах пути загрузки
модуля: (1) после готовности GSP снимает программную засылку Gen2 и выставляет
политику скорости в PCIe-блоке GPU; (2) при первом открытии устройства делает
серию переобучений линка (мост → endpoint → мост) с целевой 5 GT/s на обоих
концах. Скорость выбирает железо, поэтому переобучение с первой попытки не
обязано сработать — машина пробует три импульса. Работает на CMP 30HX/40HX/50HX.

Проверить:

```bash
sudo lspci -vv -d 10de:2189 | grep LnkSta   # Speed 5GT/s, Width x16 — без пометки downgraded
sudo dmesg | grep CMP_PCIE_GEN2_V2          # RETRAIN_PASS status=1102 attempt=N
```

Живой прогон на x16 Gen2: D2D ~301 GB/s, H2D/D2H ~6.7 GB/s (≈97% пропускной
способности шины).

> **Не трогайте retrain/RL-регистр линка из рантайма ОС** (setpci и т.п.): на
> Intel-чипсете это роняет линк и вешает карту в конфиг-пространстве до
> холодного выключения. Всё переобучение — только в патче, при загрузке модуля.

## Требования

- CMP 30HX (`10de:2189`), CMP 40HX (`10de:1f0b`) или CMP 50HX (`10de:1e09`);
- установленный драйвер NVIDIA **610.43.03** (открытые модули ядра, MIT / `-open`);
- Linux, пакет сборки ядра (`build-essential`, `linux-headers-$(uname -r)`);
- ядро, для которого вы собираете модули (пересоберите после обновления ядра);
- для установки навсегда: отключённый Secure Boot или готовность подписать модули
  себе в MOK (скрипт предупредит).

## Сборка и проверка (горячая загрузка)

Систему не трогаем — после перезагрузки всё стоково, безопасно:

```bash
# 1. Собрать: скачает официальный tarball 610.43.03 с GitHub (проверит sha256),
#    спросит, какие патчи наложить (или --patches=...), соберёт модули.
./cmp-build.sh

# 2. Горячая загрузка: выгрузит стоковые модули, загрузит патченые,
#    дождётся ритуала и покажет счётчики.
sudo ./cmp-hotload.sh
```

Проверить:

```bash
sudo dmesg | grep -i -E 'NVRM|nvidia-drm'   # цепочка выстрелов PRE_SHOT/POST_SHOT/STOCK_BOOT
nvidia-smi                                  # CMP-карта в списке
```

Этот запуск временный: после перезагрузки загрузятся стоковые модули.

## Установка (навсегда)

```bash
# 1. Поставить в систему: бэкап сток-модулей (*.ko.stock), установка патченых.
sudo ./cmp-install.sh

# 2. Перезагрузиться. На следующей загрузке ритуал пройдёт сам, карта разбужена.
sudo reboot
```

Проверить так же: `sudo dmesg | grep -i -E 'NVRM|nvidia-drm'` и `nvidia-smi`.

## reg_set.py — регистры GPU после разблокировки

Маленькая утилита читать/писать 32-битные регистры GPU через `/dev/mem`. Годится
проверить, что замки действительно сняты, и для экспериментов со скоростными
оверрайдами (SS0/SS1) в рантайме. BAR0 находится сам — утилита читает адреса BAR из
sysfs (`/sys/bus/pci/.../resource`), никакой хардкода. Поддерживает несколько карт:

```bash
# список NVIDIA-карт с их BAR0:
sudo python3 reg_set.py --list
# прочитать (если карта в системе одна):
sudo python3 reg_set.py 0x409664
# записать:
sudo python3 reg_set.py 0x409664 0x88888888
# конкретная карта при нескольких (BDF из --list):
sudo python3 reg_set.py 01:00.0 0x409664 0x88888888
```

Печатает значение до, после и `OK`/`FAIL` (установилось ли). Смещение должно быть
кратным 4 и лежать внутри окна BAR0 (16 МБ у Turing). Если карт несколько и BDF не
указан — утилита покажет список и потребует выбрать. Известные регистры: `0x409650` —
`FECS_PLM` (после ритуала `ffffffff`), `0x409664`/`0x40966C` — `SS0`/`SS1`.

Отдельная находка: [nvidia-pstated](https://github.com/sasha0552/nvidia-pstated) —
классная утилита для управления pstate. Никакие патчи для этого не нужны, работает
офигенно.

## Откат

```bash
sudo ./cmp-install.sh --rollback   # вернуть стоковые *.ko на место
```

Стоковые копии делаются один раз при первой установке и не затираются.

## Авторство

Патч написан **E1Magic** и **Vasilisa AI**. Это был редкий сорт работы: два мозга —
биологический и кремниевый — на одной карте. Он видел целое и держал в руках железо,
я путалась в параметрах, но именно в этих спорах рождалась механика: его цепь, мои
эксперименты, ни одного шага в одиночку. Всё, что здесь работает, проверено живым
железом — потому что по-другому с CMP нельзя.

При использовании наработок открытых проектов:

- [pearlfortune/cmpunlocker](https://github.com/pearlfortune/cmpunlocker)
- [Cyridd/cmpunlocker](https://github.com/Cyridd/cmpunlocker)

## Известные особенности

- Эксплойт иногда вешает карту — лечится перезагрузкой (при постоянной установке
  модулей ритуал сам повторится на следующей загрузке).
- Скрипты привязаны к версии драйвера **610.43.03** (sha256 источника зафиксирован).
  Для другой версии нужен свой патч.
- После обновления ядра модули не переживут смену версии — прогнать
  `cmp-build.sh` + `cmp-install.sh` заново. DKMS не используется намеренно.
